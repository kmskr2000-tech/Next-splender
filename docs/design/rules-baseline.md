# 기본 룰 베이스라인 (rules-baseline)

- 상태: 초안 v0.1 (기획팀) / 결정 D6 근거 문서
- 출처: 참조작 `/home/user/pokemon-splendor` (읽기 전용) 코드에서 추출한 "실제 구현된 룰". 설계 문서(참조작 주석이 언급하는 "design doc 2.1/2.2/3")는 참조 저장소에 존재하지 않아 확인 못 함 (미확인).
- 세계관 중립 문서. 포켓몬 고유 명칭은 아래 치환표를 따른다. 카드 이름·dex 번호·스프라이트 등 IP 요소는 추출 대상이 아니다.
- 근거 표기: `파일:함수/라인`. 경로 기준 `src/`. E = `core/engine.js`, C = `core/constants.js`, S = `net/session.js`, P = `net/protocol.js`, D = `data/cards.js`.
- IP/라이선스 주의: 룰 구조(수치·흐름)만 차용. 카드 데이터 표(D)는 생성 스크립트 산출물이며 이름이 IP이므로 그대로 복사 금지. 신작은 수치 분포만 참고하고 카드는 새로 생성할 것.

## 1. 구성물

### 1.1 토큰 (C:7-9, E:createGame 172-173)
- 색 토큰 5종. 색당 수량: 2인 4개 / 3인 5개 / 4인 7개 (`TOKENS_PER_COLOR`). 공식 스플렌더와 동일.
- 특수자원 5개 고정 (인원 무관) (`MASTER_TOTAL`).
- 지원 인원 2~4명, 그 외 예외 throw (E:143).
- 토큰 보유 상한 10 (`MAX_TOKENS`), 예약 슬롯 상한 3 (`MAX_HAND`), 승리 기준점 21 (`WIN_POINTS`).

### 1.2 카드 (D 집계, 총 90장. 카운트는 grep 집계 기준)
| 티어 | 장수 | 점수 | 비용(색) | 보너스 | 승급 |
|---|---|---|---|---|---|
| T1 | 35 | 0점 대부분, 1점 5장 | 색 3~4개 합 4~5 수준(예: 4단일, 2+1, 1+1+1) | 단일 색 1개 | 30장이 T2로 승급, 5장은 승급 없음 |
| T2 | 30 | 1점 12 / 2점 12 / 3점 6 | 합 5~7 수준 (2~3색) | 단일 색 1개 | 12장이 T3로 승급, 18장은 종단 |
| T3 | 15 | 3점~5점 (3:5장 정도, 4, 5) | 합 7~12 수준 (일부 단일색 6) | 단일 색 1개 | 종단 (승급 대상 없음) |
| R(희귀) | 5 | 3~4점 | 2색, 합 6~9 | 2색 각 +1 (배열 2개) | 없음 |
| L(전설) | 5 | 4~6점 | 2~3색, 합 8~13 | 2색 각 +1 | 없음 |

- 비용/점수의 정확한 표는 부록 없이 "분포 요약"만 기록 (전체 나열 금지 지시). T3·R·L은 소수라 위 범위가 거의 전수 (T3 점수 3~5, R 점수 3/3/3/4/4, L 점수 4/4/5/5/6).
- 색 보너스 분포: T1~T3는 색당 균등하게 배분되도록 생성됨 (생성 스크립트 "balance spread 0.177", D:1). 정확한 균등도는 미확인.
- 카드 스키마: `{id, tier, name, cost{색:n}, bonus(색 또는 [색,색]), points, evolvesTo(id|null), evolveReq({색:n}|null)}`. 누락된 색 키 = 0 (D:2-4).
- **승급 라인**: T1→T2→T3 3단 라인 12개, T1→T2 2단 라인 18개, 단일(T1 종단) 5개 = 총 35라인. (T1 30 → T2 30 일대일, T2 12 → T3 12 일대일 기준 추정. 일대일 여부는 id 매핑 전수 확인을 안 함 → 미확인. T3 15장 중 12장만 승급 목적지; 나머지 3장은 라인 없는 독립 카드로 보임. 미확인)
- **승급 요건(evolveReq)**: 전수 단일 색 요건 (복수 색 요건 grep 0건). T1→T2는 해당 색 보너스 3 이상, T2→T3는 4 이상(일부 5). T2의 T3 요건 5는 3장 (grep 집계). 요건 색은 카드 자신의 보너스 색과 무관하게 임의.
- 덱/테이블 (C:16-19): 티어별 별도 덱. 테이블 슬롯 T1·T2·T3 각 4칸, R 1칸, L 1칸 (`TABLE_SLOTS`). 시작 시 각 덱을 셔플(시드 기반 RNG)하고 슬롯을 채움 (E:175-180).
- 덱이 비면 슬롯은 null로 남는다 (E:takeFromTable 307).

### 1.3 귀족(보너스 타일) 대응물
- **없음.** 귀족/보너스 타일 데이터와 방문 로직이 코드 어디에도 존재하지 않는다 (`src` 전체 grep: engine에 2건은 `tileId`, view에 1건은 UI). 공식 스플렌더의 "귀족 방문"은 참조작에서 **승급(진화) 시스템 + 특수 티어 R/L 카드가 대체**한 구조로 판단. 신작에서 귀족 대응물을 둘지는 열린 질문(§7).
- `tileId`는 플레이어 외형 식별자일 뿐 (E:createGame 153).

## 2. 턴 구조

### 2.1 페이즈 상태 기계 (C:21-26, E:applyAction 245-274)
`action` → (토큰 > 10이면 `discard`) → (승급 가능하면 `evolve`) → 턴 종료. 상태 필드 `phase`, `current`, `turn`.
- 각 액션은 자기 페이즈에서만 합법 (`phaseOf` 매핑, 위반 시 `wrong_phase`). 게임 종료 후 `game_over`.
- applyAction은 입력 상태를 변이하지 않고 새 상태를 반환 (structuredClone, E:249). 순수 함수 + 시드 RNG → 결정론적 재현 가능.

### 2.2 행동 페이즈 (턴당 정확히 1개 선택)
1. **서로 다른 색 토큰 가져오기 `takeBalls`** (E:doTakeBalls 276, `takeBallSizes` 198)
   - 가져올 색은 서로 달라야 함 (`duplicate_color`), 각 색 재고 ≥1 (`supply_empty`), 색 토큰만 (특수자원 불가).
   - 장수 규칙: 재고가 있는 색 종류 수 K 기준. K ≥ 3이면 **정확히 3개**. K = 2면 1 또는 2개. K = 1이면 1개. K = 0이면 불가.
   - (공식 룰은 "최대 3개까지 가져오기 가능, 상황에 따라 적게"; 참조작은 K≥3일 때 3개 강제. 가져오는 수가 K 미만일 수 있는 건 K≤2 경우만.)
2. **같은 색 2개 가져오기 `takeTwo`** (E:doTakeTwo 293)
   - 해당 색 재고 ≥ 4일 때만 (`supply_too_low`). 공식과 동일 (4인 7개, 3인 5개, 2인 4개 모두 시작부터 가능).
3. **예약 `reserve`** (E:doReserve 311)
   - 예약 슬롯 <3 (`hand_full`). 대상: 테이블의 T1~T3 공개 카드 또는 T1/T2/T3 덱 맨 위(비공개). 덱이 비면 `deck_empty`. **R/L 카드는 예약 불가** (`cannot_reserve`, E:316/322).
   - 테이블 카드를 가져가면 해당 슬롯을 같은 티어 덱에서 즉시 보충.
   - 특수자원 재고가 >0이면 1개를 즉시 획득, 없으면 못 받고 예약은 성공 (`gotMaster` false).
4. **구매 `buy`** (E:doBuy 340, `computePayment` 61, `validatePayment` 81)
   - 대상: 본인 예약 슬롯 카드 또는 테이블의 공개 카드(T1~T3, R, L). 덱 카드는 불가.
   - 실질 비용 = 색별 `max(0, cost - 보유 색 보너스)`. 보너스 = 필드 카드 + 하위 카드 더미의 보너스 합 (이중 보너스 카드는 두 색 각 +1) (E:getBonuses 28-38).
   - 부족분은 특수자원 1:1 대체. 지불 토큰은 공급처로 반환.
   - `payment` 미지정 시 자동 계산(색 토큰 우선, 부족분만 특수자원, E:352-354). 명시 지불 시 검증: 색별 과다 지불 불가(`overpay`), 특수자원 개수는 정확히 (부족분 + 특수카드 추가분)이어야 함. 즉 색 토큰을 가지고 있어도 자발적으로 특수자원을 대신 낼 수는 있다 (색 지불 < need이면 부족분이 늘어남).
   - **특수 카드(R/L) 추가 요구**: 정상 비용에 **추가로 특수자원 1개** 필요 (`RULE_CHOICES.specialMasterIsExtra=true`, `specialMasterCount=1`, C:29-35; `requiredExtraMasters` E:75). 부족분 대체용 특수자원과 별개로 더해짐. 특수자원이 없으면 R/L 구매 불가.
   - 구매한 카드는 필드(`tableau`)에 추가. 테이블 카드였으면 슬롯 보충.
5. **패스 `pass`** (E:doPass 374): 다른 합법 행동이 하나도 없을 때만 허용 (`pass_not_allowed`). 연속 패스 수 `passStreak`가 인원 수 이상이면 교착(stalled)으로 게임 즉시 종료.
   - `passStreak`은 패스가 아닌 모든 행동에서 0으로 리셋. 타임아웃은 해당 카운터에 영향 없음.

### 2.3 반환 페이즈 (E:afterAction 434, doDiscard 395)
- 행동 직후 토큰 합(특수자원 포함) > 10이면 `discard` 페이즈. 정확히 `초과분`만큼 반환해야 함 (`bad_discard_count`). 어떤 토큰이든(방금 가져온 것·특수자원 포함) 선택 가능. 반환 토큰은 공급처로.
- 토큰이 10 이하가 되면 반환 페이즈 없음. 반환 후 승급 페이즈 검사로 이동.
- 예약으로 특수자원을 받아 11개가 되는 경우도 동일 처리.

### 2.4 승급 페이즈 (E:evolveOptions 105, doEvolve 414, toEvolvePhase 442)
- 행동(+반환) 후 승급 가능한 카드가 하나라도 있으면 `evolve` 페이즈. 선택지: `evolve {cardId}` 1회 또는 `skipEvolve` (선택 사항). 1턴 최대 1회 승급, 승급 후 즉시 턴 종료.
- 승급 가능 조건: 필드 카드 X가 `evolvesTo`·`evolveReq`를 가지고, (a) `evolveReq`의 모든 색에 대해 본인 보너스(필드+하위 더미, X 자신 포함) ≥ 요구값, (b) 대상 카드(id)가 **본인 예약 슬롯에 있거나 테이블에 공개된 상태**. 예약 슬롯 우선 판정 (E:111-114).
- 승급은 **무료** (토큰 지불 없음). X는 필드에서 빠져 하위 카드 더미(`evolved`)로, 대상 카드가 같은 위치에 들어감 (E:424-426).
- 점수는 필드 카드만 합산 (`getPoints` E:40). 따라서 X의 점수는 사라지고 대상 카드 점수로 대체된다. X의 보너스는 유지(하위 더미 보너스 포함, 주석: "official rule", E:33).
- 대상이 테이블 카드였으면 슬롯 보충. 예약 슬롯 카드였으면 슬롯이 비어 예약 가능 수 증가.
- 방금 구매한 카드는 같은 턴에 승급 요건 충족 시 즉시 승급 가능 (구매→승급 페이즈 순).
- 패스·타임아웃으로 끝난 턴에는 승급 페이즈 없음.

### 2.5 귀족 방문 시점
- 해당 없음 (귀족 없음, §1.3).

### 2.6 턴 종료·게임 종료 (E:endTurn 448, finishGame 463)
- 턴 종료 시(승급 후 포함) 현재 플레이어 점수 ≥ 21이고 아직 종료 트리거가 없으면 `endTriggeredBy` 기록. 트리거 검사는 **승급 이후**에 한다 (승급이 점수를 바꿀 수 있으므로, E:447 주석).
- 다음 플레이어가 **시작 플레이어**로 돌아오면 게임 종료. 즉 모든 플레이어가 같은 턴 수를 가진다 (공식과 동일). 시작 플레이어는 시드 RNG로 무작위 (E:182).
- 트리거는 한 번 걸리면 유지 (이후 점수가 21 미만으로 내려가도 취소되지 않음).
- 교착 종료(`stalled`): §2.2-5.

### 2.7 승리 점수·동점 (E:getRanking 120)
- 점수 = 필드 카드 점수 합. 승리 기준점 21 (공식 15와 다름).
- 순위 정렬: 1) 점수 높음, 2) **승급 횟수**(하위 카드 더미 장수) 많음, 3) **필드 카드 수 적음**, 4) 위 셋이 같으면 동률(같은 rank 공유 → 공동 승자 가능). 정렬 단 플레이어 번호는 표시 순서용일 뿐 rank에는 반영 안 됨 (E:131).
- 공식은 "구매 카드 수 적은 쪽" 타이브레이커. 참조작은 그 앞에 "승급 횟수 많음"이 추가.

## 3. 공식 스플렌더와 다른 점 (참조작 고유 룰)

1. 승리 점수 21 (공식 15).
2. 귀족 없음. 대신 승급 시스템.
3. **승급(진화) 시스템**: 색 보너스 N 이상 + 대상 카드가 예약 슬롯/테이블에 있을 때 무료로 카드 교체. 점수는 대체, 보너스는 누적 유지. 타이브레이커에 승급 횟수 사용.
4. **특수 티어 R/L**: 별도 덱·슬롯(각 1칸), 예약 불가, 이중 보너스(2색 각 +1), 구매 시 특수자원 1개 추가 필요.
5. 카드 수: T1 35 / T2 30 / T3 15 (공식 40/30/20) + R5 + L5 = 90 (공식 90 + 귀족 10).
6. 테이블: 티어당 4칸 (공식 동일) + R·L 각 1칸.
7. 토큰 가져오기: K ≥ 3이면 3개 강제 (공식은 가능한 만큼 적게 가져오기도 허용하는 해석 존재).
8. 예약 시 특수자원 지급은 공식과 동일하나, 지급할 게 없어도 예약 가능 (공식과 동일).
9. 패스: 합법 행동이 없을 때만 허용 + 한 바퀴 연속 패스 시 게임 강제 종료 (공식에는 없음).
10. 턴 타임아웃(멀티): 강제 턴 스킵 (§5).
11. 보너스 토큰 수량표가 공식과 동일 (4/5/7 + 5)이고 3인 "색당 2개 제거", 2인 "색당 3개 제거"라는 주석 (C:8, 'WING rules')만 있고 정확한 룰북 출처는 미확인.

## 4. 데이터 스키마 초안 (신작용 중립)


## 5. 멀티플레이 구현 요약 (참조작)

- **서버 권위 아님.** WebRTC DataChannel 기반 P2P, **호스트-게스트 + 락스텝 결정론** (P:1-2, S:beginGame 387-420). 모든 클라이언트가 같은 시드로 같은 엔진을 로컬 실행. 시작 메시지 `START {seed, names, turnLimitMs, aiNames}`.
- 액션 흐름: 게스트가 로컬 적용 후 `ACTION {action}`을 호스트에 전송 → 호스트가 엔진에 적용해 성공하면 다른 피어에 브로드캐스트 `{from, action, h}` (S:hostMsg 240-251). 게스트는 수신 액션을 적용하고 상태 해시 `h`와 비교, 불일치면 `SYNC_REQ` → 호스트가 **전체 상태**를 `SYNC`로 전송 (S:357-371). 해시는 FNV-1a 32bit, 대상 필드는 rng/current/turn/phase/supply/table id/덱 길이/플레이어 토큰·필드·예약·하위 더미 id/endTriggeredBy (P:canonState 59).
- 전송은 순서 보장·신뢰성 채널 가정. 시그널링: 수동 코드 복붙 또는 방 코드(fireroom/peerroom).
- **타임아웃**: 기본 턴 제한 45초 (`DEFAULT_TURN_LIMIT_MS`, S:11), 호스트 방 설정으로 변경 가능. 호스트만 1초 간격 타이머로 감시, 만료 시 사람 플레이어에 `{type:'timeout'}` 적용·브로드캐스트·타이머 리셋 (S:startTurnTimer 434-463). AI 좌석은 타임아웃 제외. 타이머는 모든 성공 액션(페이즈 전환 포함)마다 리셋.
- **재접속/이탈**: 연결 끊긴 좌석은 호스트가 즉시 AI(hard)로 대체; 재접속 시 `HELLO {rejoin: idx}` → `REJOIN_OK {state}`로 좌석 반환. 호스트가 사라지면 게스트들이 호스트 락 경쟁으로 승격 (S:onHostGone 527~, 이후 상세 미확인). 재접속 정보는 localStorage 저장.
- 멀티는 AI 난이도 고정 hard, 도감/업적 기록 없음.

## 6. 버그 의심 / 모호한 룰

| # | 항목 | 근거 | 확신도 |
|---|---|---|---|
| B1 | **타임아웃 액션이 엔진에서 거부될 가능성 높음.** `applyAction`의 `phaseOf` 매핑에 `'timeout'`이 없어 `unknown_action` 반환(E:258). switch에는 `case 'timeout'`이 있으나 도달 불가. 호스트 타임아웃(S:445-446)이 `res.ok` 실패 시 아무 일도 안 일어나고 타이머만 리셋됨 → 사실상 턴 타임아웃 미작동. | E:252-258 vs 268, S:445 | 코드상 확정, 실행 검증은 미확인 |

| B7 | 종료 트리거 유지: 트리거 후 점수가 21 미만으로 내려가는 경로는 없어 보이나(승급이 점수를 낮추는 케이스 존재 여부는 T1→T2→T3 데이터 전수 비교 안 함), 이론상 가능하면 모호. | E:449 | 미확인 |
